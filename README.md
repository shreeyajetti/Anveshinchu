## The collection

- **Source:** the official Wikimedia dump of Telugu Wikipedia, [`tewiki-20261101-pages-articles.xml.bz2`](https://dumps.wikimedia.org/tewiki/), one XML file containing every page as wiki markup (269 MB compressed, SHA-1 `4c7c149f7ba26fa352778ea3af062071c536299b`).
- **Kept:** every article, i.e. every page in the main namespace (0) that is not a redirect: **130,227 articles**.
- **Skipped:** redirects and pages in other namespaces (talk, user, template, category, file, ...).
- **One document = one article**, indexed as *title + plain text*.

The dump is streamed directly from the `.bz2` file with `xml.etree.ElementTree.iterparse`, one `<page>` at a time, so it is never decompressed to disk or loaded whole into memory. Wiki markup is reduced to plain text:

```
'''గుంటూరు''' [[ఆంధ్ర ప్రదేశ్]] లోని ఒక [[నగరం|నగరము]].<ref>...</ref> {{Infobox ...}} [[వర్గం:నగరాలు]]
    ->  గుంటూరు ఆంధ్ర ప్రదేశ్ లోని ఒక నగరము.
```

Templates `{{...}}`, tables `{|...|}`, references, comments, images, categories and HTML tags are removed, and links `[[target|label]]` keep only their label. The local names of the File and Category namespaces (దస్త్రం, వర్గం) are read from the dump's own `<siteinfo>`.

## The indexing pipeline

```
 XML dump ─► wikidump ─► Tokenizer ─► Normalizer ─► Indexer ─────────► SPIMI blocks ─► merge ─► vocabulary.tsv (in memory)
 (.bz2)      (stream,    (letter/     (ZWNJ, NFKC,  (positions per     (2M positions    (k-way)   postings.txt   (on disk)
             clean)       mark runs)   digits)       term and doc)      each, on disk)
```

Documents and queries go through **the same** `analyze()` function (tokenize, then normalize), so a query term always has the same form as an indexed term.

### Tokenizer (`src/tokenizer.py`)

Telugu puts spaces between words, but neither obvious way of splitting works:

```python
>>> "విక్రమ్‌ సారాభాయ్ 500 కి.మీ.".split()
['విక్రమ్\u200c', 'సారాభాయ్', '500', 'కి.మీ.']          # punctuation and an invisible ZWNJ stay attached

>>> re.findall(r"\w+", "విక్రమ్ సారాభాయ్ అంతరిక్ష కేంద్రం")
['వ', 'క', 'రమ', 'స', 'ర', 'భ', 'య', 'అ', 'తర', 'క', 'ష', 'క', 'ద', 'ర']   # every word shredded
```

A Telugu syllable is a consonant plus vowel signs (ా ి ీ ు …) and the virama (్). Unicode classifies these as **combining marks**, not letters, and Python's `\w` doesn't count marks as word characters, so it cuts words apart at every vowel sign. Over a third of all characters in Telugu text are such marks.

A token is therefore a maximal run of Unicode **letters, marks and numbers** (plus the zero-width joiners). Everything else (spaces, punctuation, symbols) separates tokens.

### Normalizer (`src/normalizer.py`)

- **Remove zero-width joiners** (U+200C ZWNJ, U+200D ZWJ). They only change how a word is drawn: హెమింగ్‌వే (with ZWNJ) and హెమింగ్వే (without) are the same word to a reader and must be the same term.
- **Remove a stray Devanagari nukta** (U+093C) that is not attached to a Devanagari letter.
- **Unicode NFKC** composes equivalent character sequences into one form (ె + ౖ → ై) and folds full-width characters.
- **Telugu digits → ASCII** (౨౦౧౧ → 2011), so both forms match.
- **Lowercase** Latin letters.
- No stop-word removal and no stemming: phrase queries need every word's position.

### Indexer (`src/indexer.py`)

The normalized terms of each document are numbered 0, 1, 2, … and each position is appended to that term's postings:

```python
postings: dict[str, dict[int, list[int]]]    # term -> {doc_id -> sorted positions}
"గుంటూరు": {1: [0, 1, 25, ...], 2: [...], ...}
```

For every term: **document frequency** df = the number of documents containing it (the length of its postings list), and **collection frequency** cf = its total number of occurrences (the sum of all its positions).

### Storage on disk (`src/storage.py`): vocabulary in memory, postings on disk

The full Telugu Wikipedia has 52,527,950 positions, far too many to hold as Python lists in memory (the machine this was built on had under 3 GB of free RAM). The index is therefore built with **SPIMI** (single-pass in-memory indexing):

1. Articles are indexed in memory until the current block holds 2 million positions.
2. The block is written to `index/blocks/block_NNNN.tsv`, sorted by term, and memory is freed.
3. After the last article, all blocks are merged in one pass (a k-way merge with `heapq.merge`). Doc IDs increase from block to block, so a term's merged postings are its block postings joined in order.
4. The merge writes `postings.txt` and, for every term, one line of `vocabulary.tsv`. The blocks are deleted.

| File | Contents | Where it lives when searching |
|---|---|---|
| `vocabulary.tsv` | `term  df  cf  offset  length` (sorted by term) | **main memory** |
| `postings.txt` | `term TAB doc:pos,pos,...;doc:pos,...` (one line per term) | **disk**; one line is read per query term |
| `docs.tsv` | `doc_id  Wikipedia page ID  number of terms  text offset  text length  title` | main memory (small) |
| `store.jsonl` | the indexed text of each article, for snippets | disk |
| `meta.json` | collection description and statistics | main memory |

Example (from the real index):

```
vocabulary.tsv   గుంటూరు  3005  5723  145145863  37844
postings.txt     గుంటూరు  1:0,2,12,49,61,80,89,183,234,265,284,303,495,504,506,534,835,846,857,863,869,909,911,914,916,940,950,9 ...
docs.tsv         1  786  1049  124  22532  గుంటూరు జిల్లా
```

To read a postings list, the program looks the term up in the in-memory vocabulary (binary search over the sorted terms), **seeks** to `offset` in `postings.txt` and reads exactly `length` bytes. Nothing else of the postings file is read. The vocabulary is held as a sorted list of terms plus four integer arrays (`array` module) rather than a dict of tuples, which takes about a third of the memory.

All files are UTF-8 text with Telugu stored as-is (not as `\u` escapes), so every file can be opened and checked by hand. Every file is opened with an explicit `encoding="utf-8"`, because the Windows default (cp1252) can't encode Telugu.

## Why positional indexing?

A basic inverted index records only **which** documents contain a term. That is enough for boolean queries, but not for phrases: `తెలుగు AND సినిమా` matches any article containing both words anywhere, while the phrase `"తెలుగు సినిమా"` ("Telugu cinema") should match only where the two words are **next to each other, in that order**.

- **Phrase** `t1 t2 … tn`: keep the start positions *p* where *t1* is at *p*, *t2* at *p+1*, …, *tn* at *p+n−1*.
- **Proximity** `t1 /k t2`: find position pairs with |pos(t1) − pos(t2)| ≤ k, in either order, with a two-pointer sliding window over the two sorted position lists.

All positions of a term in a document are stored, not only the first one, otherwise a phrase starting at a later occurrence would be missed. Punctuation doesn't take up a position.

Requires Python 3.10 or newer. There are no third-party dependencies.

```bash

.venv\Scripts\activate            # Windows   (macOS/Linux: source .venv/bin/activate)
python -m unittest -v             # 37 tests (1 expected failure documents the suffix gap)
```

From Python:

```python
from src.storage import load_index
from src.search import search, snippet

index = load_index("index")              # loads vocabulary.tsv + docs.tsv; postings stay on disk
print(index.df("గుంటూరు"), index.cf("గుంటూరు"))
for r in search(index, '"తెలుగు సినిమా"')[:3]:
    print(r.docid, r.title, r.matches, snippet(index, r.doc_id, r.matches[0]))
```

### 4. Searching

```bash
python -m src.cli search "QUERY"          # --top N documents, --snippets N per document
python -m src.cli search                  # interactive prompt; empty line quits
python -m src.cli tokenize "తెలుగు వాక్యం"   # show how text is tokenized and normalized
```

| Query | Meaning |
|---|---|
| `గుంటూరు AND జిల్లా` | both terms in the article |
| `గుంటూరు జిల్లా` | implicit AND |
| `ఇంటికి OR ఇంట్లో` | either term |
| `గుంటూరు AND NOT జిల్లా` | first term, but not the second |
| `(సినిమా OR నాటకం) AND నటి` | parentheses for grouping |
| `"తెలుగు సినిమా"` | **phrase**: terms adjacent, in this order |
| `సినిమా /3 దర్శకత్వం` | **proximity**: within 3 positions, either order |

Precedence: `NOT` > `AND` > `OR`. Query words go through the same tokenizer and normalizer as the documents. Each result shows the internal doc ID, the Wikipedia page ID, the article title and the matched positions with a snippet (match in 【】).

> **Windows PowerShell** strips double quotes inside a command-line argument. Use `「తెలుగు సినిమా」` for a phrase on the command line, or type it at the interactive prompt. Add `--translit` to any command if your terminal draws Telugu incorrectly (`గ్రామంలో` prints as `grāmaṁlō`).

### 5. Output file

```bash
python -m src.make_output               # writes output.txt
```

[`output.txt`](output.txt) contains the index statistics, **10 rare terms with their df, cf and full positional postings** (chosen at random with a fixed seed from the terms with df ≤ 3), and **5 test cases**, each of which checks its result independently against the postings read from disk:

1. Storage and retrieval: the in-memory vocabulary entry points exactly at the term's postings line on disk; df and cf match the postings.
2. Tokenizer and normalizer: ZWNJ, punctuation and Telugu digits.
3. Boolean query `గుంటూరు AND జిల్లా AND NOT ప్రకాశం`, compared with set operations on the postings.
4. Phrase query `"తెలుగు సినిమా"`, with the adjacent positions shown.
5. Proximity query `సినిమా /3 దర్శకత్వం`, compared with a brute-force check of all position pairs.

## Extra: ranked retrieval and evaluation

Beyond the assignment, the same index code supports BM25 ranking (`src/ranking.py`), evaluated on the [MIRACL](https://huggingface.co/datasets/miracl/miracl) Telugu benchmark: 828 questions with Wikipedia passages judged relevant by native speakers. Because the judgments refer to MIRACL passage IDs, this runs on a separate MIRACL index (29,268 passages):

```bash
python -m src.fetch_miracl                                  # data/passages.jsonl (subset of MIRACL Telugu)
python -m src.cli build --source miracl --index index-miracl
python -m src.evaluate                                      # --report reports/evaluation.md for every question
```

| Exact terms, no stemming | Success | Recall | nDCG@10 | MRR@10 |
|---|---:|---:|---:|---:|
| Boolean AND (whole result set) | 12.7% | 12.3% | | |
| BM25 (top 10) | 62.8% | 62.5% | 0.444 | 0.390 |

*Success* = at least one relevant passage retrieved; *Recall* = share of relevant passages retrieved. AND returns nothing at all for 80% of questions, because one differently suffixed word empties the result. These numbers are optimistic in absolute terms: the subset is 18× smaller than the full MIRACL corpus and two thirds of it comes from judged articles.

## Limitations

- **Suffixed forms don't match.** Telugu attaches case endings to words (ఇల్లు "house", ఇంటికి "to the house", ఇంట్లో "in the house"), and every form is a separate term. This is recorded as an expected-failure test; a rule-based stemmer is the next step.
- **Wiki markup cleaning is regex-based.** A few markup fragments survive in unusual articles (about 45 in the first 2,000 articles).
- **Positions cross sentence boundaries,** because punctuation isn't a position.
- **The postings file is plain text,** not compressed, so it is larger than a binary, gap-encoded format would be; in exchange it can be read and verified by hand.
